# Inactive optional nutrition export (#727)

Canonical SQL `nutrition_meals` is the only meal store. Ordinary ChatGPT food logging never calls this export service or requires a phone. `NutritionExportStore.queue` consumes existing authenticated-owner context plus trusted confirmation of an exact half-open occurrence period (from inclusive, to exclusive; maximum 62 days/1000 meals/1 MiB). Never deserialize `PeriodAuthority` or reconciliation authority from model/client JSON. P12-09 owns future trusted composition; no tool or production route is registered here.

Queue snapshots preserve stable IDs/idempotency keys, source revision, occurrence offsets, components, kcal/g and nullable unknown macros. Existing queue entries or meals already marked exported are skipped, never reset by another period request. Modern snapshots expire pending eligibility after seven days; native-write/receipt evidence is retained rather than purged into an unsafe re-export. Imported legacy queue credentials are not active: rows without the new source revision cannot be claimed.

Device claim/complete routes are an explicitly callable, inactive factory. Root auth permits only the two POST export routes through an injected `nutritionExportAuth` verifier. The verifier must check signature/hash, server-bound owner, nutrition-export-only scope, expiry and current revocation on every request. No verifier/credentials are installed or issued in production; absence fails closed. An export capability cannot authenticate ordinary Jarvis routes, and ordinary user/agent/upload credentials cannot act as export-device credentials. No replacement login or permission grant is introduced.

Claim limit defaults to ten (1–20), with a five-minute lease capped by device expiry. Request JSON is limited to 16 KiB; response to 256 KiB and each item to 64 KiB. Owner-local transaction locks, conditional row selection and current canonical revision/tombstone checks prevent concurrent devices from claiming the same snapshot. Cancellation/transient deadlock retries occur before any returned native-write instructions. A repeated claim operation key returns `reconciliation-required` with no items, never replayed Health write instructions after response loss. New keys cannot reclaim old claimed/uncertain rows.

Completion ACKs carry exact item ID, server claim UUID, written/failed, writer (default Apple Shortcuts, ≤100) and optional failure error (≤500). Same-device identical receipts can replay even after the original lease; conflicting receipts, other devices/owners, padded IDs and unacknowledged expired claims are refused. Expiry commits uncertainty before reporting conflict. Failed completion is conservatively uncertain because partial native effects may exist. Corrections/deletions preserve canonical measurements and snapshot values: pending becomes cancelled, claimed uncertain, and written out_of_sync. Export access synchronizes queue state against all current canonical revisions; ACK of a stale issued snapshot cannot mark the corrected meal written.

Trusted owner reconciliation records checked-in-Health evidence: all samples present, all absent, or partial/unknown. No recovery path resets pending or issues another native write. Partial evidence can later be resolved; absence remains terminal `reconciled_absent`, requiring a separately reviewed replacement policy. No server transaction proves exactly-once native Apple Health effects, deletes native samples or ingest exported nutrition back into Jarvis.
