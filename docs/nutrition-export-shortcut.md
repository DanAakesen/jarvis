# Optional on-demand nutrition export: unverified phone guide

This is guidance for a future separately approved physical-iPhone check, **not an installable, signed, built or tested Shortcut**. No phone settings or credentials are changed by this repository. The coordinator verified the original pure Shortcut contract: claim, native Log Health Sample for dietary energy and available macros at `occurredAt`, then complete each item. No additional native search/identifier/atomic-journal capability is asserted here.

Normal ChatGPT food logging is independent. SQL meals remain canonical; suggestions and plans are not eaten food. Export runs only after trusted owner confirmation of the exact period and a separate on-demand phone action; never add it to morning/evening routines or notifications, and never re-ingest exported nutrition from Health.

Before any native writes, separately verify scoped revocable export-device provisioning and HTTPS server configuration, Health permissions/types/units/time interpretation, durable local per-claim/per-item write/receipt tracking, and reconciliation on this specific phone. Use no human password, broad ingest token or model-selected URL/owner. These services are not registered and no production credential is supplied. If the needed capability/journal is unavailable, stop before writing.

The intended future protocol is:

1. Owner confirms the exact half-open period through trusted existing Jarvis confirmation metadata. The server snapshots canonical meals; the Shortcut cannot select arbitrary owners or queue periods itself. Generation/registration of that owner tool remains P12-09.
2. Send POST `/daily/nutrition/export/claim` using only the approved export-device capability, with a newly generated operation key and optional limit 1–20. Retries of that request must use the same key. A repeated key returns `reconciliation-required` with **no items**; never replace it with a new key to recover old write instructions. Persist the first claim UUID/items/lease in an approved durable phone journal before touching Health. A claim is not a Health write.
3. For a new claim, preserve each item’s occurrence instant, kcal/g units and exact supplied values. Write dietary energy and only known macros; skip null unknowns, retain explicit zero values where the native action supports them. Verify the actual native actions/types and zero-value behavior on the phone; no source schema or sample contents are invented here. Each available nutrient is a separate native effect, so a crash may leave a partial meal.
4. Track completed native actions locally. After all required samples for an item are known written, POST `/daily/nutrition/export/complete` with its exact ID/claim UUID and status written. Retry only that identical ACK after response loss; it never authorizes another native write. Changed writer/status/error conflicts are refused. For partial/unknown failure, report failed with a bounded diagnostic, not written; do not blindly start the native writes again.
5. On expired claim, lost response/journal, ambiguous existing samples, correction/deletion or failed/out_of_sync/uncertain state, stop writes and reconcile privately in Health with the owner. Mere timestamp/value equality may be ambiguous when meals share those values; no native stable-ID support is verified. Do not guess absence, fabricate samples or delete native data automatically. The trusted owner recovery service records all-present/all-absent/partial evidence but does **not** requeue. Replacement/deletion of native samples needs its own verified protocol/approval.

Physical acceptance must demonstrate no duplicates across claim/ACK loss, partial writes, lease expiry, crashes and multiple devices, while preserving unknowns, timezones and canonical corrections/tombstones. Server synthetic/SQL tests cannot establish exactly-once Health effects. Device provisioning, activation, live/private sample reconciliation and this acceptance remain open under #727; original Daily continues normal authorized writes and remains canonical before migration cutover gates pass.
